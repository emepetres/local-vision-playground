# Spike: OpenVINO 2026.4 and NPU driver 32.0.100.4023+ (#78)

Done on the `experiment/openvino-2026.4` branch, on the demo machine (ASUS Zenbook S14,
Intel Core Ultra 7 258V), with the existing INT4-sym 2B IR — not re-exported.

## What changed

- `openvino`, `openvino-genai` and `openvino-tokenizers` pinned at `2026.4.0` in the
  `convert` group of `vision/pyproject.toml`; `uv.lock` re-resolved, and only those three
  packages moved.
- `NPU_DRIVER_FLOOR` (committed ahead of the pins, in the same branch) in `vision/tools/convert/convert.py` and the prerequisite table in
  `vision/tools/convert/README.md` raised from `32.0.100.3104` to `32.0.100.4023`.
- The demo machine's NPU driver was already `32.0.100.4512` when the spike started, so
  the driver was **not** the variable between the two Benchmarks below. Only OpenVINO moved.

## Result

The existing IR loads and generates on CPU, iGPU and NPU under 2026.4.0. No row failed.

Both Benchmarks: same Frame, 5 repetitions, driver 4512, current `main`-line code. Records:
`docs/benchmarks/*openvino-2026-3-0-n-20261104-204407.*` (2026.3.0) and
`*openvino-2026-4-0-n-20261104-204740.*` (2026.4.0).

| Variant | Load 2026.3 → 2026.4 | Median 2026.3 → 2026.4 | Tokens/s 2026.3 → 2026.4 |
| --- | --- | --- | --- |
| Foundry Local CPU | 6.4 → 5.7 s | 8.8 → 9.4 s | 10.4 → 9.8 |
| OpenVINO CPU | 5.5 → 6.0 s | 4.77 → 5.09 s | 26.8 → 25.2 |
| OpenVINO iGPU | 4.3 → 13.7 s (4.9 s warm) | 2.34 → 2.40 s | 54.7 → 53.4 |
| OpenVINO NPU | 3.8 → 39.0 s (2.7 s warm) | 5.29 → 5.60 s | 24.2 → 22.9 |

- **Load time.** The first load on iGPU and NPU after the upgrade is much slower (13.7 s
  and 39.0 s against 4.3 s and 3.8 s). The probable cause is that the compiled-model cache
  built under 2026.3 is not reused, but the records only show slow-then-fast; the cause is
  inferred, not isolated. A second Benchmark of those two Variants (`*20261104-204838.*`)
  loaded in 4.9 s (iGPU, against 4.3 s) and 2.7 s (NPU, against 3.8 s). Before the demo,
  load each Variant once on 2026.4 so the first load is not paid on stage.
- **TTFT.** Not measured: the Benchmark records carry no first-token timing. The "First"
  column is the cold full inference, not time to first token, so nothing here answers the
  TTFT half of the question.
- **Tokens per second.** No gain: throughput is 2–6 % lower on every OpenVINO row.
  Foundry Local's row, which does not use these packages, moved by a similar 6 %, and the
  iGPU row differs by 9 % between the two 2026.4 Benchmarks (53.4 against 48.4), so the
  difference is within run-to-run noise. One Benchmark per version, so no firmer claim.
- **Output.** Every OpenVINO row still hits the 128-token limit with repetition loops
  (5/5), exactly as on 2026.3 — 2026.4 does not fix that, and it is a Recipe matter.

## Returning to 2026.3.0 and driver 3104

OpenVINO (pure git, no machine state):

```bash
git checkout main -- vision/pyproject.toml vision/uv.lock   # or: git revert the spike commit
cd vision && uv sync --group convert
uv pip list | grep -i openvino                               # expect 2026.3.0
```

Or simply switch back to a branch that does not carry the spike. Expect one slow first load per
Variant on iGPU and NPU after switching back.

NPU driver: the demo machine runs 4512, never 3104, during this spike, so no rollback
to 3104 was exercised here. To go back: Device Manager → Neural processors →
Intel(R) AI Boost → Driver → *Roll Back Driver* if Windows still holds the previous one;
otherwise install the 32.0.100.3104 package from Intel's download centre. Verify with
`Get-CimInstance Win32_PnPSignedDriver | ? DeviceName -match 'AI Boost'`. Lowering the
floor back is a one-line change to `NPU_DRIVER_FLOOR` and the README row.
